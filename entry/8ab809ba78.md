ライブラリ名はGyakuと言います。依存性の逆転から取っています。

スター下さい！

[https://github.com/mkizka/gyaku:embed]

`@gyaku/di`という名前で[npm](https://npmx.dev/package/@gyaku/di)にも公開しています。

## 特徴

gyakuは`using`で破棄処理が書けて、`async`なファクトリ関数をサポートするDIライブラリです。

以下のように書けます。ここに書いてあることがだいたい全てです。

```ts
import { setTimeout } from "node:timers/promises";

import { createRegistry } from "@gyaku/di";

const createGreeter = async ({ name }: { name: string }) => {
  await setTimeout(100);
  return {
    say: () => console.log(`hello, ${name}`),
    [Symbol.asyncDispose]: async () => {
      await setTimeout(100);
      console.log(`bye, ${name}`);
    },
  };
};

const registry = createRegistry()
  .value("name", "gyaku")
  .service("greeter", ["name"], createGreeter);

{
  await using services = await registry.resolve();
  services.greeter.say();
  // hello, gyaku
}
// bye, gyaku
```

[typed-inject](https://github.com/nicojs/typed-inject)に大きな影響を受けていて、APIはほぼ同じといっていいです。

差分としてはこのあたりです。

- injectClassに相当するものが(現状は)ない
  - classを使う機会が減っているため
- resolveはキー指定がなく全てまとめて解決
- `using`でdispose処理をまとめて行う

APIについては出来れば違う書き味のものにしたかったんですが、いろいろ試行錯誤した結果メソッドチェーンで繋げて最後に解決するこの形に落ち着きました。理由は後述します。

## なぜ作ったか

[NestJSが好きだけどきつかったから2週間でWebフレームワーク作った ( ZeltJS )](https://zenn.dev/9wick/articles/363b51112106d0) という記事を読んでライブラリを作ってみたくなったからです。

自分用にライブラリを作ったことは何度かありましたが、AIに指示しながらであれば自分では作ろうと思わない分野のものも作れるのではと思いました。

また、ちょうどDIライブラリであるtyped-injectを試していて、無視できるレベルであるものの若干変えたいところがあると感じていたところでもありました。

### 非同期ファクトリを使いたい

まずtyped-injectでは非同期関数を使ったファクトリが書けません。DIにおける初期化処理で非同期処理を書くことはあまり無いのですが、書けた方がうれしいケースもあるはずです。

例えばDBクライアントの初期化です。以下は`pg`を使う場合の例です。

```ts
import { Client } from "pg";

const createDb = async (config: Config) => {
  const db = new Client({ connectionString: config.DATABASE_URL });
  await db.connect();
  return db;
};
```

これを同期処理にする場合2つの方法が考えられます。まず初期化を先に完了させておいてから、DIコンテナに組み込むパターンです。

```ts
const db = new Client({ connectionString: process.env.DATABASE_URL });
await db.connect();

const app = createContainer().provideValue("db", db);
```

typed-injectと同じくDIライブラリである[awilix](https://github.com/jeffijoe/awilix)の[非同期ファクトリーに関する機能リクエストissue](https://github.com/jeffijoe/awilix/issues/12)ではこの方法が紹介されていました。ただしこの方法では、少し工夫しないとDB接続情報をDIコンテナから受け取れません。

次に、別のサービスのメソッドまたはDIコンテナの外で実行する方法です。

```ts
const createDb = (config: Config) => {
  const client = new Client({ connectionString: config.DATABASE_URL });
  return client;
};

// 中略

const db = container.resolve("db");
await db.connect();
```

まあ...正直大抵の場合はこれでよいと思います。しいて言えば非同期処理の返り値をDI出来ませんが、まれなケースだと思います。

gyakuではそのようなまれなケースのために、非同期処理と同期処理を同じAPIでサポートします。

デメリットとしては、全てのファクトリが同期関数だったとしても`resolve`には`await`が必要です。

### 位置引数を使いたくない

typed-injectは依存関係を`inject`というフィールドに記述し、引数に順番に注入します。

これをパラメータプロパティでフィールドに入れて使うのがREADMEにも書かれている書き方でした。

```ts
class HttpClient {
  constructor(private log: Logger) {}
  public static inject = ["logger"] as const;
}
```

これはこれでいいのですが、TypeScriptの`erasableSyntaxOnly`を使っていきたかったのでその点だけが微妙でした。

以下のように書くことも出来るのですが、依存が増えるごとに倍の行数が必要です。

```ts
class HttpClient {
  private log;
  // ここにフィールドが増えていく
  constructor(log: Logger) {
    this.log = log;
    // ここにthisが増えていく
  }
  public static inject = ["logger"] as const;
}
```

しかし、引数にオブジェクトとして渡されるのがデフォルトであれば以下のように書くことも出来ます。

```ts
class HttpClient {
  private deps;
  constructor(deps: { logger: Logger }) {
    this.deps = deps; // 使うときはthis.deps.loggerで呼び出す
  }
  public static inject = ["logger"] as const;
}
```

これはこれで微妙と思う人も多そうですが、個人的には引数が十分多い時はオブジェクトにまとめて渡す方が好きです。

そこでgyakuでは全てのファクトリにオブジェクトで依存関係を渡すようにしています。しかもこれはawilixのようなプロキシではなく、純粋なオブジェクトです。

### usingを使いたい

タイトルに書いておきながら、正直これは既存ライブラリと差別化するために入れたおまけです。

typed-injectはprovideされたクラスが`dispose`メソッドを持っていると、Injectorの`dispose`メソッドを使ってまとめて呼び出すことが出来ます。

```ts
class Foo {
  constructor() {
    console.log("Foo created");
  }
  dispose() {
    console.log("Foo disposed");
  }
}
const rootInjector = createInjector();
const fooProvider = rootInjector.provideClass("foo", Foo);
fooProvider.resolve("foo"); // => "Foo created"
await rootInjector.dispose(); // => "Foo disposed"
fooProvider.resolve("foo"); // Error: Injector already disposed
```

しかし現代のNode.jsは`using`が使えるので、独自メソッドではなく`[Symbol.dispose]`や`[Symbol.asyncDispose]`を使いたいところです。

gyakuではファクトリの返り値がこれらのメソッドを持っている場合、`await using`によってスコープを抜けるタイミングでまとめて実行します。

## やらなかったこと

### 関数一つでまとめて依存関係を宣言

当初は依存関係の宣言を一つの関数にまとめようとしていました。以下のようなイメージです。

```ts
const container = define({
  name: provide("gyaku"),
  greeter: provide(["name"], createGreeter),
});
```

これはこれで動くものが作れたのですが、型がやや複雑になってしまいました。

依存関係で指定したキーがそれより前に宣言されていることを型チェックで検出出来るようにしたかったので、型の表現が見た目にそぐわない気がしています。

そこで結局、gyakuはtyped-injectと同じメソッドチェーンになりました。

```ts
type ServiceRegistry<
  Services extends ServiceMap,
  DepsMap extends DepsMapBase<Services>,
> = {
  /* */
};

// 以下のメソッドは全てServiceRegistry<...>を返す
const registry = createRegistry()
  .value("name", "gyaku")
  .service("greeter", ["name"], createGreeter);
```

こう書くことで`value`や`service`を呼ぶごとに`ServiceRegistry`のジェネリクス部分に再帰的に依存関係が積みあがっていきます。

実装も同様にイミュータブルなオブジェクトを繰り返し返すようにしています。型と実装が一貫している良い実装になっていると思います。

### デコレーター

これはtyped-injectを使っていた理由でもあるのですが、デコレーターがなんとなく苦手で不採用にしています。

Spring Bootなどの印象で魔法感があり、見た目通り動くのが良いと思います。型チェックもそこそこ魔法をやっていますが...。

デコレーターについては[tc39のproposalsがStage3からStage2.7に下がった](https://zenn.dev/cybozu_frontend/articles/web-standards-trends-202605)という話もあり、素直に使える日はまだ遠そうです。

### resolve("key")で依存関係を部分的に解決

一般的なDIライブラリでは、DIコンテナのうち一部のキーだけを解決する機能がだいたい備わっていると思います。

gyakuにはこの機能が今のところはなく、resolveしたタイミングで全てのファクトリを実行します。

なぜこうなっているのかというと、disposeの処理タイミングを簡単に決められなくなるからです。例えば共通の`db`に依存する`fooRepository`と`barRepository`があったとします。

```
fooRepository ─┐
               ├─→ db
barRepository ─┘
```

ここで`fooRepository`と`barRepository`を個別に解決した場合、`fooRepository`をdisposeしたタイミングでも`barRepository`はまだ`db`を使いたいので`db`だけdisposeしない...のような制御が必要です。

gyakuはusingを自然に使うために、個別に依存解決をさせるのではなく全てのファクトリをまとめて実行させるようにしました。いっそ分かりやすいんじゃないかと思います。

## AIに作らせてみての所感

gyakuは全体で300行ほどの小さい実装で、これくらいであれば何の工夫もなく狙った通りの実装を作ってくれます。

一方でいくつか気にした方が良さそうなこともありました。

### 細かい仕様をAIと議論する

一見動くものが出来るのですが、その分細かい仕様を見落としがちです。最近話題の[grill-me](https://www.skills.sh/mattpocock/skills/grill-me)スキルを使うなどして仕様を詰めていくのが良いと思いました。

例えばgyakuでは最初は依存関係の解決時に発生したエラーを`AggregateError`に詰めて投げていたのですが、これだと発生したエラーがどのファクトリから発生したものかが分からないようになっていました。

AIと議論してユーザーがどうやってエラーハンドリング出来るべきかを検討して、後からカスタムエラーを追加しています。

### AIに理解度テストを出させる

AIに実装させるとはいえ、全ての行をレビューしてなるべく全体を理解したものにしたいと考えていました。

そこで「数行ずつ実装を解説して。理解度テストを出して、正解したら次に進んで」などと指示をして、実装内容を理解できるようにしていました。

この理解度テストを出してもらうのが結構良く、ただ解説してもらうより頭に入ってくる気がします。

一方でこのクイズのクオリティに結構差があったと感じていて、選択肢より自由回答になるようにプロンプトで誘導した方がいいかもしれません。
